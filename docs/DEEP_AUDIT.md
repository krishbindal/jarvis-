# JARVIS-X — source audit, verified behavior and remaining limitations

**Scope:** Review of current `main` and the implementation in PR #27 (November 2026).
Reviewed representative startup, orchestration, Qt UI, command routing, structured AI
parsing, action registry, automation planning/execution, agent loop, model providers,
privacy/approval controls, voice integration and CI. **This is not a proof that every
line or third-party integration was tested.**

## Confirmed problems repaired in PR #27

| Area | File(s) | Problem | Fix |
| --- | --- | --- | --- |
| Automation | `automation/executor.py` | Missing `success` field was treated as true; planner's `message` could claim work was done | Explicit Boolean result required, result-based summary, stop on failure |
| Multi-step | `core/app.py` | Could emit a result before setting the final message; could describe a failed chain as completed | Emit a complete, evidence-based result after the last actual step |
| AI execution | `core/app.py`, `core/plan_guard.py` | AI action proposals could include unregistered skills, oversized plans, non-dict extras or forged approval fields | Reject entire invalid plan, cap to three supported steps, separate model-code permission |
| Agent loop | `core/app.py` | Empty/unverified plan or tool failures could surface the model's “task complete” message | Never claim completion without executor results; describe uncertainty |
| Concurrency | `core/app.py` | A new daemon thread was created for every command, racing over shared task state | One active command; extra requests get an explicit busy response |
| Unknown commands | `core/command_router.py` | Generic unknown commands were routed to generated Python | Use an explicit safe fallback instead of automatic code generation |
| URL/file opening | `core/action_registry.py`, `core/target_safety.py` | Unsafe URI schemes, executable local targets, ignored browser refusal, incorrect “3 attempts” failure message | Reject executable URI schemes; require executable-file approval; check browser response; report actual handler failures |
| Qt dashboard | `ui/main_window.py`, `ui/styles.qss` | Limited state visibility and rich text interpretation of user/tool strings | Readable mission-control layout, permission status, literal text insertion, bounded timeline, explicit result state |
| QA | `tests/`, `scripts/ci_headless_benchmark.py` | No direct regression tests for many failure/unverified cases | Tests for malformed tool outputs, unsupported actions, forged approvals, concurrency, unsafe open targets; headless Qt widget checks |

## What test outcomes actually establish

Consult the **latest PR #27 GitHub Actions run**, including the exact head SHA,
`Ran N tests` output, `pip check`, total measured coverage, and benchmark artifacts.
Do not add together tests from different workflow runs. The `coverage.json`
artifact is the source of truth for statement/branch coverage.

The headless Windows Qt screenshot is generated by the actual PySide6 code
on a CI runner. Hosted Windows image font availability, offscreen composition,
and graphics settings can differ significantly from the user's laptop. It is
**not** a visual-appearance certification.

Executor `success=True` is a report from a tool wrapper. It is **not** independent
evidence that an application is visible, an email arrived, a site loaded, or
a file was modified correctly. The status UI explains this limitation.

## Remaining engineering work, in priority order

1. **P1 — Independent post-action verification:** where practical, verify
   observed files/URLs/window accessibility/send confirmations after an executor
   returns success; build typed per-tool evidence records, timeouts, retries and
   idempotency safeguards. Tests should simulate false-positive OS launches.
2. **P1 — Real stop/cancellation:** the current Stop button cancels approvals,
   TTS and autonomy requests but does not forcibly kill all already-running
   external subprocesses. Implement cooperative cancellation tokens through
   agent/automation/download and blocking API paths before calling it a
   full emergency stop.
3. **P1 — Prompt-injection resilience:** the system uses allowlists and approvals,
   but retrieved web, screen and MCP content can still influence an LLM.
   Keep untrusted text in lower-trust data fields, verify URLs/domains, and
   test realistic instruction-in-document fixtures end-to-end.
4. **P1 — Runtime privacy controls:** add a persistent recording/screen-sharing
   indicator, account-specific cloud consent, provider retention disclosures,
   and sensitive data redaction for diagnostics/memory exports.
5. **P1 — Windows acceptance:** run real microphone, Vosk/OpenWakeWord,
   TTS/speakers, Qt approval dialogs, app/window automation, MCP integrations,
   Groq/Gemini/Ollama, multi-monitor scaling, suspend/resume, repeated shutdown
   and long-running resource tests on an actual Windows laptop. Record raw
   observations, machine specs and redacted logs.
6. **P2 — Coverage and reliability:** expand integration tests for command
   routing, core orchestration, action executors, memory and UI interaction;
   report line and branch coverage per module, not only a whole-project figure.
7. **P2 — Distribution:** package a signed/tested Windows application with
   optional speech-model provisioning and documented rollback/uninstall.

## Hallucination policy

It is not technically possible to guarantee that a generative model never
produces incorrect text. This project instead makes **tool calls conditional
on supported schemas and approvals** and makes **task completion claims
conditional on executor reports**. Unverified external outcomes must stay
explicitly labeled as such.

See `docs/RELEASE_READINESS.md` for device-level acceptance criteria.
